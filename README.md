# Forte Guard · Madagascar

Локальный MVP для кейса ForteBank на Datathon ’26. Полный путь обработки:

```text
MOV → кадры с таймкодами → YOLO + ByteTrack → object journal
    → действия и состояния → action journal
    → [правила в коде ∥ локальная LLM] → объединение кандидатов
    → минимальная проверка ссылок → доказательства → API / интерфейс
```

**Рабочий контур, который команда может улучшать по модулям.** Верификация сейчас структурная: проверяются ссылки, интервалы, сессии, значения связанных состояний, доступные возможности распознавания и существование кадров. Отдельный VLM-верификатор кандидатов не запускается.

## Запуск

Python 3.11–3.13; для текущего проверенного окружения использовался Python 3.12. Нужен локальный Ollama. Команды выполняются из корня репозитория.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -e '.[vision,dev]'
python scripts/setup.py
python scripts/prepare_models.py
ollama pull gemma4:26b
forte-guard serve
```

Откройте **http://127.0.0.1:8000**. API-ключ создан в `.env`, поле `FORTE_API_KEY`. Скопируйте его в интерфейс. Swagger: `/docs`.

Подготовка моделей требует интернета один раз. По умолчанию `prepare_models.py` скачивает дообученный детектор команды `models/detector-v2.pt` из приватного релиза `detector-v2` (нужен `gh auth login`); для YOLO-World или YOLOE-26 — `--detector world|yoloe`, веса сохраняются с подготовленным словарём; при обработке видео веса не скачиваются и автоустановка пакетов отключена. Ollama вызывается только через loopback или внутренний Docker-сервис `ollama`. Телеметрия Ultralytics отключена. Видео, кадры и логи облачным AI не отправляются.

LLM можно вынести на GPU-машину команды: `FORTE_OLLAMA_URL=http://<IP>:11434`. Допускаются только loopback, Docker-сервис `ollama` и литеральные частные или Tailscale-адреса (`10.*`, `192.168.*`, `100.64.0.0/10`); имена хостов отклоняются, чтобы DNS не увёл запросы во внешний сервис. По умолчанию одна модель `gemma4:26b` (понимает изображения) работает и резонером, и для зон, и судьёй бенчмарка: на GPU держится одна модель вместо двух. Если поставить текстовую модель вроде `qwen3:30b`, для зон нужна отдельная vision-модель: `FORTE_ZONE_MODEL=gemma4:26b`. Запросы идут с `think: false`.

Детектор по умолчанию — `detector-v2` (YOLO26m, обучен на 960 px по черновой разметке для 33 обучающих роликов, разметка не проверена людьми; рук и состояний открыт/закрыт нет; сервис запускает его на 640 px). На бенчмарке 42 видео с `FORTE_CASHIER_PRESENCE=zone`: найдено 9 из 22 нарушений, 5 ложных срабатываний, средняя ошибка таймкода 5 с (`detector-v1`: 8 из 22, 4 ложных, 18 с). Ролики пересекаются с обучением, поэтому цифры завышены. YOLO-World с текстовыми классами из `config/detector.json` остаётся вариантом: `FORTE_DETECTOR=world`, `FORTE_MODEL_PATH=models/cashier-world.pt`. Можно включить YOLOE-26 (`yoloe-26s-seg`): `FORTE_DETECTOR=yoloe`, `FORTE_MODEL_PATH=models/cashier-yoloe26.pt` и `python scripts/prepare_models.py --detector yoloe`. По умолчанию он выключен, пока бенчмарк не покажет пользу; какой из них точнее на ваших видео, не измерено. Дообучение детектора — [docs/training.md](docs/training.md). Настройка классов, зон и обучение на локальной разметке — следующая работа команды.

## Проверка одного видео без интерфейса

```bash
forte-guard analyze /path/to/video.mov --output data/my-run
```

Зоны оператор не задаёт: сервис определяет их сам после детекции. Рабочее место кассира — там, где человек дольше всех стоит и рядом с ним рабочие предметы (счётная машинка, ноутбук, сейф); клиентская сторона — где появляются остальные люди; стол — где деньги и документы лежат неподвижно; хранилище и выход — по сейфу и двери. Если кассира или стол по трекам определить нельзя, недостающие зоны дополняет локальная vision-модель (`FORTE_ZONE_MODEL`) по кадру с наибольшим числом людей. Неопределённые зоны остаются неизвестными, а не угадываются. Если в `config/zones.json` заполнен профиль камеры, используется он. Автоматические зоны требуют проверки.

Сразу после детектора, до автозон и журнала, треки чинятся (`FORTE_TRACK_REPAIR=true`, по умолчанию): ByteTrack не смотрит на класс, поэтому трек получает один класс внутри пары деньги/документ; трек денег или человека, оборванный на пару кадров, однозначно склеивается с продолжением того же класса рядом; маленький неподвижный «человек» (отражение кассира в стеклянной двери) не считается человеком. Результаты и ограничения — [docs/known-errors.md](docs/known-errors.md).

Уход кассира с рабочего места по умолчанию определяется режимом `zone` (`FORTE_CASHIER_PRESENCE=zone`); режим `track` фиксирует уход, только когда трек кассира виден вне его зоны. Режим `zone` смотрит на само рабочее место: кассир на месте, если в зоне виден любой человек, кроме клиента, или рука; уход — если зона пуста 3 с после исчезновения у края зоны или у двери и 6 с после исчезновения посреди зоны, а остальной кадр при этом детектируется. Режим не зависит от обрывов трека. На бенчмарке с detector-v1 (42 видео): найдено столько же нарушений, что и с `track` (8 из 22), ложных срабатываний 4 вместо 5.

```bash
forte-guard analyze /path/to/video.mov --zones /path/to/zones.json --output data/my-run
```

Для запуска без LLM: `--no-llm`. Для работы над журналом без детектора: `--replay /path/to/object_journal.json`. Replay — явный режим разработки; отсутствующие веса никогда не заменяются тестовыми данными автоматически.

## Что сохраняется после каждого этапа

В `data/jobs/<job_id>/`:

| Артефакт | Содержимое |
| --- | --- |
| `frames.json`, `frames/` | Реально извлечённые JPEG и их таймкоды |
| `object_journal.json` | Нормализованные боксы, классы, track ID, уверенность, признаки состояния |
| `zones.json` | Профиль зон конкретного запуска |
| `action_journal.json` | Действия, интервалы состояний, роли, пачки, поддерживаемые и неподдерживаемые наблюдения |
| `candidates.rules.json` | Результат детерминированной ветки |
| `candidates.llm.json` | Результат локальной LLM |
| `candidates.json` | Объединённые кандидаты с происхождением и результатом минимальной проверки |
| `catalog_snapshot.json`, `run_config.json` | Каталог и несекретные параметры запуска |
| `result.json` | Итоговый API-ответ с JPEG в base64 |

Обе ветки получают один action journal и один каталог правил/сценариев. LLM выбирает только существующие `rule_id`, `event_ids`, `state_ids`. Таймкоды и нормативные ссылки подставляются кодом. Журнал передаётся в компактном табличном JSON без удаления действий или интервалов; при превышении контекста или таймауте ветка явно сообщает об ограничении.

`open_labels.xlsx` и прежние результаты не читаются во время анализа. Они могут использоваться отдельно после запуска для оценки.

## API для жюри

Все маршруты `/api/v1/*` требуют `X-API-Key`. Секрет не передаётся в URL.

Для публичного сайта задайте `FORTE_WEB_ACCESS=guest`: любой посетитель без ключа загружает видео и видит только свои проверки (подписанная HttpOnly-cookie `SameSite=Lax`), а чужие задачи, в том числе видео жюри, бенчмарк, конфигурация и readiness открываются только по ключу. Чтобы интерфейс не спрашивал ключ и показывал всю историю, задайте `FORTE_WEB_ACCESS=open` — только во внутренней сети. При открытии страницы браузер получает HttpOnly-cookie с `SameSite=Strict`, производную от ключа; сам ключ на страницу не попадает, а запросы без ключа и без этой cookie по-прежнему отклоняются. `trusted_clients` выдаёт такую cookie только адресам из `FORTE_ALLOWED_CLIENTS`. По умолчанию (`api_key`) интерфейс просит ключ. Загрузки из интерфейса без ключа ограничены с запасом: не больше 10 видео в очереди (`FORTE_UI_MAX_QUEUED`) и 60 загрузок в час (`FORTE_UI_MAX_UPLOADS_PER_HOUR`), сверх лимита — HTTP 429. Загрузки с `X-API-Key` (жюри) не ограничиваются.

```bash
curl -X POST http://127.0.0.1:8000/api/v1/analyze \
  -H "X-API-Key: <ваш ключ>" -F "file=@/path/to/video.mov"

curl http://127.0.0.1:8000/api/v1/jobs/<job_id> \
  -H "X-API-Key: <ваш ключ>"
```

Загрузка возвращает HTTP 202 и `job_id`. Статусы: `processing`, `done`, `failed`. Готовый ответ содержит `verdict: violation | no_violation`, `violations` с `type`, `timecode_sec`, `description`, `evidence_frames` (1–3 JPEG в base64). Дополнительно возвращаются предупреждения, происхождение кандидата, нормативная ссылка и статистика этапов.

Вспомогательные маршруты:

- `GET /api/v1/jobs` — список задач;
- `GET /api/v1/jobs/{id}/artifacts/{name}` — журнал/кандидаты/параметры этапа;
- `GET /api/v1/jobs/{id}/frames/{frame_id}` — кадр;
- `GET /api/v1/jobs/{id}/video` — исходная запись;
- `GET /api/v1/config` — несекретные настройки;
- `GET /api/v1/readiness` — готовность конфигурации, зависимостей, весов, хранилища и локальной LLM (200 / 503);
- `GET /health` — состояние сервиса без доступа к видео.

Настраиваемый лимит задачи — 285 секунд, включая ожидание в очереди. Обрабатывается одна задача за раз; это сохраняет ограниченное потребление GPU/RAM. Это не гарантия производительности на любом оборудовании или при массовой одновременной загрузке. Для внешнего доступа сервис разворачивается на машине команды за HTTPS-прокси. Текущий локальный запуск сам по себе не предоставляет публичный URL.

`create_demo_job.py` добавляет явно подписанную синтетическую задачу в историю интерфейса. Она проверяет интеграцию после детектора, а не точность YOLO. Тесты используют только синтетические данные и подменяют внешние модели; настоящих видео и запросов в облако в CI нет.

## Бенчмарк на размеченных видео

Раздел «Бенчмарк» в интерфейсе (кнопка **Run benchmark**) прогоняет все размеченные видео через тот же конвейер, что и обычная проверка, и сравнивает ответы с разметкой команды.

```bash
FORTE_BENCHMARK_ENABLED=true
FORTE_BENCHMARK_LABELS=https://docs.google.com/spreadsheets/d/<id>/edit?gid=<gid>
FORTE_BENCHMARK_VIDEOS=/path/to/videos
```

Таблица — Google Sheets с доступом по ссылке или локальный CSV с колонками «наименование файла», «таймстемп», «нарушение / без нарушения», «комментарий». Имена с латинской X и кириллической Х считаются одинаковыми.

- Вердикт по видео: TP / FN / FP / TN; сбой или превышение лимита считаются ошибкой, как у жюри.
- Таймкод: ближайшее нарушение сервиса к времени разметки, попадание в ±3 с и средняя ошибка.
- Строгий recall (`strict_recall`): доля видео с нарушением, где верен и вердикт, и таймкод (±3 с) — ближе к тому, как жюри смотрит на К1 и К2 вместе.
- Судья — локальная LLM (`FORTE_JUDGE_MODEL`, по умолчанию `FORTE_LLM_MODEL`): по комментарию решает, то ли это нарушение и верен ли тип. Вызывается только для найденных нарушений.
- Прогоны сохраняются в `data/benchmarks/<run_id>/` вместе с версией кода, моделями и отпечатком разметки; кадры после видео удаляются, журналы и `result.json` остаются.

Автодеплой перезапускает dev-сервис на каждый коммит в `main`, и идущий там прогон прерывается. Для замера, который не оборвётся, запустите свою копию: `scripts/bench_copy.sh` (порт 8001, только loopback) берёт настройки, веса, разметку и видео dev-сервиса на Mac, хранит задачи отдельно в `~/forte-bench-data` и работает на коде вашего checkout. Затем откройте `http://127.0.0.1:8001` → «Бенчмарк».

Разметка читается только после того, как конвейер выдал ответ по видео, и в конвейер не передаётся. Видео ставятся в очередь по одному: загрузка пользователя выполнится между двумя видео бенчмарка, но её ожидание входит в лимит задачи. Поэтому во время проверки жюри бенчмарк не запускают и держат `FORTE_BENCHMARK_ENABLED=false`. Перезапуск сервиса (в том числе автодеплой) прерывает прогон.

## Поддержка и ограничения базовой версии

Проверить работающий сервис целиком через HTTP, включая настоящие модели:

```bash
python scripts/check_service.py
python scripts/check_service.py --video /path/to/video.mov
```

Проверка загружает видео в обычную очередь, получает журналы обеих веток, JPEG и диапазон исходного видео для плеера. В терминал выводятся этапы и статистика; содержимое записи и ключ не печатаются.

- Реализованы треки, оценка ролей по зонам, интервалы присутствия, взаимодействия рук с объектами, предполагаемые передачи денег, перемещение в зону хранения, наблюдения документов/устройств и переходы состояний, если их выдал детектор.
- Потеря детекции превращается в `unknown`, а не автоматически в «кассир ушёл». Пустое место в журнале не означает невыполненное действие.
- Ключевые операции вроде достоверного пересчёта, идентификации, проверки подлинности, замка и пломбы базовой геометрией не распознаются. Они перечислены в `unsupported_actions`. Правило пропущенного пересчёта отключено до появления такого распознавателя и подтверждения покрытия/исключений.
- История пачек имеет контракт для родительских связей; надёжное распознавание физического разделения/слияния пачек ещё нужно реализовать. Базовый трекер не восстанавливает потерянные деньги как ту же пачку без доказательств.
- Нормативный каталог — начальный набор гипотез с `source_status: needs_review`; действующие редакции, трактовки и исключения должны быть проверены командой. Эти статусы видны в ответе.
- Вердикт `no_violation` означает, что включённые проверки не дали поддержанного кандидата. Он не подтверждает полную корректность операции.
- Точность на отложенных видео и другом ракурсе ещё не измерена. Числа `confidence` не являются откалиброванными вероятностями.

В конфигурации можно заменить детектор: `FORTE_DETECTOR=yolo`, `FORTE_MODEL_PATH=models/your-finetuned.pt`. Названия классов задаются вашими весами; алиасы — в `config/detector.json`. После изменения словаря или переключения между `yoloe` и `world` снова выполните подготовку весов.

Исходные интерфейсы библиотек: [YOLOE](https://docs.ultralytics.com/models/yoloe/), [YOLO-World](https://docs.ultralytics.com/models/yolo-world/), [tracking](https://docs.ultralytics.com/modes/track/), [Ollama API](https://docs.ollama.com/api/chat). Библиотеки и веса распространяются по собственным лицензиям.

## Docker

Сначала подготовьте веса и `.env` на машине с интернетом. Затем:

```bash
docker compose build
docker compose up -d
docker compose exec ollama ollama pull gemma4:26b
```

Модели Ollama хранятся в отдельном томе, YOLO — в `models/`. После подготовки обработка не требует интернета. Compose по умолчанию публикует интерфейс только на `127.0.0.1:8000`. На Linux используется CPU; для NVIDIA настройте PyTorch/CUDA и GPU-доступ контейнера под свою машину.

Приватные материалы (`videos/`, `data/`, `models/`, `.env`, разметка и прошлые отчёты) исключены из Git.
