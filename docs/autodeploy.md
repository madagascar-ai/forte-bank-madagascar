# Автодеплой на Mac

```text
push / merge в main → Tests в GitHub Actions → локальный агент → новая версия сервиса
```

Агент проверяет текущий `main` примерно каждые 30 секунд. Он допускает только успешный push-run workflow `tests.yml` для того же SHA и того же репозитория. Ветки разработчиков и pull request не развёртываются. Если main уже изменился за время подготовки, устаревший кандидат пропускается. Переписанная история `main` (force-push) не блокирует обновление: локальное зеркало принимает новую вершину, а выкатывается по-прежнему только SHA с зелёным CI.

Перед обновлением готовятся отдельная копия кода и окружение Python. Одинаковые наборы зависимостей используют одно окружение; при изменении `pyproject.toml` или `constraints-runtime.txt` создаётся новое. Параметры запуска берутся из локального `.env`. Изображения, журналы операций, ключи и модели не отправляются в GitHub.

Во время переключения SQLite запрещает приём новых задач и позволяет завершить принятые. Только после опустошения очереди API перезапускается. Новая версия должна ответить на health с нужным SHA и пройти авторизованную readiness-проверку. Если проверка не проходит, агент запускает предыдущий код с его окружением. Существующие результаты сохраняются и во время обновления остаются доступны до короткого перезапуска API.

## Где работает сервис

Рабочий каталог macOS:

```text
~/Library/Application Support/ForteGuard/
  .env                  локальные настройки и исходный API-ключ
  data/                 общая история задач, видео и кадры
  models/               локальные веса YOLO
  releases/<sha>/       версии кода
  envs/<hash>/          окружения Python
  status.json           состояние обновления без секретов
  live.json             активная версия
  logs/                 локальные логи API, подготовки и агента
```

Рабочий Git checkout участников остаётся отдельным. После первичной настройки изменение `.env` в checkout влияет на разработку; параметры общего сервиса меняются в `.env` рабочего каталога выше. API-ключ при переносе сохраняется. Список `FORTE_ALLOWED_CLIENTS` также сохраняется и продолжает ограничивать доступ устройств.

Веса, словарь и модель Ollama готовятся отдельно от деплоя кода. Если новый словарь не совпадает с весами или Ollama недоступна, подготовка не проходит, а текущий API продолжает работать. После устранения причины агент повторяет неудачную попытку через пять минут.

## Первичная установка

Сначала подготовьте обычное окружение и модели по README. Нужна существующая авторизация Git через macOS Keychain с чтением приватного репозитория и результатов Actions.

Из корня checkout:

```bash
.venv/bin/python scripts/autodeploy.py bootstrap --workspace "$PWD"
```

После push дождитесь успешного CI. Подготовить конкретный проверенный коммит без остановки работающего API:

```bash
.venv/bin/python scripts/autodeploy.py prepare FULL_COMMIT_SHA
```

Первый перенос истории выполняется при остановленном обычном API:

```bash
.venv/bin/python scripts/autodeploy.py bootstrap --workspace "$PWD" --sync-data
.venv/bin/python scripts/autodeploy.py install
```

`--sync-data` применяется только до первого управляемого запуска. Повторное выполнение после установки не перезаписывает рабочую историю. Команда `prepare` — ручная подготовка; автоматический агент дополнительно проверяет CI и актуальность main перед активацией.

Установка создаёт пользовательский LaunchAgent `kz.forte-guard.autodeploy`. Он запускается при входе владельца в macOS, перезапускает API после сбоя и проверяет обновления. Mac должен быть включён и бодрствовать. При выходе из учётной записи сервис не работает; это ещё не отдельный круглосуточный сервер.

## Управление

```bash
.venv/bin/python scripts/autodeploy.py status
.venv/bin/python scripts/autodeploy.py stop
.venv/bin/python scripts/autodeploy.py start
```

Остановка/запуск относятся к пользовательскому LaunchAgent. `stop` выключает и API; применяйте после завершения задач. Для ручного запуска агента в терминале предусмотрена команда `run`; одновременно работает один экземпляр благодаря файловой блокировке.

Авторизованный `GET /api/v1/deployment` показывает активный SHA, стадию, предыдущий SHA и ссылку на CI. `/health` возвращает SHA запущенного процесса. Подробности ошибок остаются в локальных логах; секреты в статус не включаются.

После обновления страницы интерфейс показывает короткий SHA работающей версии в нижней части экрана.

API и веса запускаются только на Mac. Дополнительных входящих SSH-портов и GitHub runner на компьютере для этого способа не требуется.

Основа интеграции: [GitHub Actions workflow runs API](https://docs.github.com/en/rest/actions/workflow-runs?apiVersion=2022-11-28).
