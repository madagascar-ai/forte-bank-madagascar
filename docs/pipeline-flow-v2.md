# Datathon 26 — флоу системы (v2)

Весь путь одного примера через систему, от видео до JSON. На каждом шаге: что делаем → как выглядят данные → какая проблема остаётся (и зачем нужен следующий шаг).

**Что изменилось по сравнению с v1:**
- нет модели позы: руки находит сам детектор (класс `hand`);
- роли, зоны и факты считаются в одном шаге, в таблице состояний;
- сглаживание идёт после таблицы состояний и работает по ней;
- появился лог действий;
- кандидатов в нарушения ищут параллельно правила (код) и LLM по логу;
- VLM проверяет каждого кандидата по кадрам.

**Пример:** клиент передаёт кассиру деньги, кассир кладёт их на стол и уходит. Потом клиент подходит к стойке и открывает дверь.

---

## Шаг 0. Видео → кадры

Нарезаем видео на картинки, 5 кадров в секунду.

```
video_017.mov (145 с)  →  725 картинок:  t=0.0, t=0.2, ... t=145.0
```

**Проблема:** это просто картинки без смысла.

---

## Шаг 1. Детектор: что на каждом кадре

RF-DETR, дообученный на наших классах: `person, hand, money, safe, door, bag`.

```
t=10.4  person (102,52,251,401)   person (498,61,649,419)
        hand (405,240,425,265)    hand (430,245,450,262)    money (400,230,450,260)
t=17.0  person (500,60,650,420)   money (300,220,360,250)
```

**Проблема:** модель не знает, кто есть кто. Это просто «какой-то person» и «какая-то hand».

---

## Шаг 2. Трекер: кто есть кто

ByteTrack даёт каждому объекту номер, который сохраняется между кадрами.

```
t=10.4  person#1   person#2   hand#3   hand#4   money#7
t=17.0             person#2                     money#7
```

**Проблема:** есть номера, но нет смысла. Кто кассир? Чья это рука? Где касса?

> Сырые детекции с координатами (шаги 1–2) **сохраняем отдельно**. Они понадобятся на шаге 9, чтобы нарисовать боксы на кадрах-доказательствах.

---

## Шаг 3. Таблица состояний: роли, зоны, факты

Одна функция, которая в цикле по кадрам сразу считает всё нужное:

- **Роль** назначается один раз на весь трек: person#1 90% времени на кассовой стороне, значит, это кассир.
- **Зона** каждого объекта определяется по координатам: касса, стол, клиентская зона.
- **Чья рука** определяется по стороне стойки. **У кого деньги** — по пересечению бокса руки с боксом денег.

```
роли:  person#1 → cashier1    person#2 → client2

t=10.4: hand#3 на стороне кассы → cashier1, hand#4 на стороне клиента → client2,
        обе пересекают money#7 → деньги у обоих
```

Результат — таблица фактов, одна строка на каждый момент:

| t    | кассир в кассе | деньги где | деньги у кого   | клиент где  |
|------|----------------|------------|-----------------|-------------|
| 10.4 | да             | стол       | клиент + кассир | клиентская  |
| 12.0 | да             | стол       | никто           | клиентская  |
| 15.4 | **НЕТ**        | стол       | никто           | клиентская  |
| 15.6 | да             | стол       | никто           | клиентская  |
| 17.0 | нет            | стол       | никто           | клиентская  |
| 22.0 | нет            | стол       | никто           | касса?      |

**Проблема:** в 15.4 кассир «пропал» на один кадр. На самом деле он наклонился, и детектор его не увидел. Человек не может уйти и вернуться за 0,2 секунды, это ошибка, а не уход.

## Шаг 4. Сглаживание: убираем мигания

Детектор смотрит на каждый кадр отдельно и иногда ошибается на 1–2 кадрах. Сглаживание исправляет такие одиночные «мигания» в таблице фактов.

**Как:** голосование большинством в окне. Для каждого момента смотрим на него и на соседей (2 кадра до + 2 после = 5 кадров = 1 секунда) и ставим то значение, которое встречается чаще.

```
t:        15.0  15.2  15.4  15.6  15.8   ...  16.6  16.8  17.0  17.2  17.4
до:        да    да   НЕТ    да    да          да    да   НЕТ   НЕТ   НЕТ
после:     да    да    да    да    да          да    да   НЕТ   НЕТ   НЕТ
```

- 15.4: окно `[да, да, НЕТ, да, да]` → большинство «да» → мигание убрано.
- 17.0: окно `[да, да, НЕТ, НЕТ, НЕТ]` → большинство «НЕТ» → настоящий уход сохранён.

```python
def smooth(values, window=5):
    half = window // 2
    result = []
    for i in range(len(values)):
        neighbors = values[max(0, i - half): i + half + 1]
        result.append(sum(neighbors) > len(neighbors) / 2)   # большинство
    return result
```

Каждая колонка таблицы сглаживается отдельно.

**Размер окна** подбираем на наших видео. Начинаем с 1 секунды:

| Окно                          | Плюс                                   | Минус                                          |
|-------------------------------|----------------------------------------|------------------------------------------------|
| Маленькое (3 кадра = 0,6 с)   | Быстрые настоящие действия сохраняются | Мигание в 2 кадра подряд уже не уберётся       |
| Большое (15 кадров = 3 с)     | Убирает почти любой шум                | Короткое **настоящее** действие тоже сотрётся  |

**Проблема:** правилам и LLM удобнее читать не покадровую таблицу, а **список действий**.

## Шаг 5. Лог действий

Сравниваем соседние строки сглаженной таблицы и записываем, что изменилось. У каждого события есть `id`, время и уверенность. Отдельно перечисляем, **что система не умеет определять**, чтобы LLM не делала выводов об отсутствии этих действий.

```json
[
  {"id": 1, "t": 10.4, "action": "передача", "from": "client2", "to": "cashier1", "obj": "money7", "conf": 0.86},
  {"id": 2, "t": 12.0, "action": "положил",  "who": "cashier1", "obj": "money7", "where": "стол", "conf": 0.88},
  {"id": 3, "t": 17.0, "action": "покинул",  "who": "cashier1", "where": "касса", "conf": 0.84},
  {"id": 4, "t": 22.0, "action": "вошёл",    "who": "client2",  "where": "касса", "conf": 0.58},
  {"id": 5, "t": 24.0, "action": "открыл",   "who": "client2",  "obj": "door1", "conf": 0.71}
]
не_определяется: ["пересчёт денег", "проверка купюр"]
```

**Проблема:** это история того, что произошло. Теперь надо найти в ней нарушения.

## Шаг 6. Поиск кандидатов: две ветки параллельно

### 6a. Правила (код)

Известные нарушения ищутся быстро, точно и предсказуемо. На каждое правило можно написать тест.

```python
# деньги на столе, никто не держит, кассира нет > 3 сек
if есть "положил"(money, стол) и после него "покинул"(cashier) и деньги не взяли 3+ сек:
    → кандидат "unattended_cash", events=[2, 3]
```

### 6b. LLM-резонер

Читает лог и список правил словами, ловит неочевидные и новые нарушения.

```
промпт:  правила (rule_id + описание) + лог +
         "используй только события из лога,
          не делай выводов о действиях из списка не_определяется"

ответ:   [{"rule_id": "unattended_cash",       "event_ids": [2, 3]},
          {"rule_id": "outsider_in_cash_zone", "event_ids": [4]}]
```

LLM ссылается только на `event_ids` и `rule_id`. Таймкоды и ссылки на нормы она своими словами **не пишет**.

**Проблема:** кандидаты из двух веток могут повторяться, а часть может оказаться ошибкой. Например, у события 4 уверенность всего 0.58.

---

## Шаг 7. Объединение кандидатов

Одинаковые `rule_id` с пересекающимися событиями склеиваем в одного кандидата. Таймкод берём **из лога** по `event_ids`, а не из текста LLM.

```
кандидат A: unattended_cash        t=17.0   (нашли обе ветки)
кандидат B: outsider_in_cash_zone  t=22.0   (нашла только LLM)
```

**Проблема:** оба кандидата построены на логе, а лог мог ошибиться. Нужно посмотреть на **сами кадры**.

---

## Шаг 8. VLM: проверка по кадрам

Для каждого кандидата даём Qwen3-VL кадры вокруг события и задаём конкретный вопрос. Ответ — в строгом JSON.

```
A: кадры 16–20 с: "Сотрудник покинул рабочее место, оставив наличные на столе?"
   → {"visible": true,  "observation": "Сотрудник уходит, пачка купюр остаётся на столе"}  ✅

B: кадры 21–25 с: "Посторонний человек находится в кассовой зоне?"
   → {"visible": false, "observation": "Клиент стоит у стойки со своей стороны, за неё не заходит"}  ❌
```

Кандидат B отброшен: детектор ошибся с зоной, а VLM поймала ошибку по кадрам.

**Проблема:** таймкод 17.0 найден с точностью 0,2 с (5 fps), а нужен конкретный кадр.

## Шаг 9. Точный кадр и доказательства

Возвращаемся к исходным 29 fps в окне 16–18 с и находим точный момент. Берём 3 кадра и рисуем на них боксы из сохранённых детекций.

```
таймкод: 17.0 → 17.24
кадры:   16.5 (до), 17.24 (момент), 20.0 (деньги всё ещё лежат)
```

**Проблема:** нужно указать нарушенное правило и источник.

## Шаг 10. Норматив и ответ

По `rule_id` берём название и пункт документа из нашего каталога норм, который собран и проверен вручную. Описание собираем из наблюдения VLM.

```json
{
  "verdict": "violation",
  "violations": [
    {
      "type": "Наличные оставлены без присмотра",
      "timecode_sec": 17.24,
      "description": "Сотрудник уходит, пачка купюр остаётся на столе. <документ, пункт>",
      "evidence_frames": [
        {"timestamp_sec": 16.5,  "image_base64": "..."},
        {"timestamp_sec": 17.24, "image_base64": "..."},
        {"timestamp_sec": 20.0,  "image_base64": "..."}
      ]
    }
  ]
}
```

## Вся цепочка

```
видео → кадры → объекты → номера → таблица состояний → сглаживание → ЛОГ ДЕЙСТВИЙ
                                                                          │
                                                         ┌────────────────┴───────────────┐
                                                     правила (код)                 LLM по логу
                                                         └────────────────┬───────────────┘
                                                                     кандидаты
                                                                          │
                                                            VLM проверяет по кадрам
                                                                          │
                                                          точный кадр → норматив → JSON
```

| Шаги | Что это                                              |
|------|------------------------------------------------------|
| 0    | Подготовка: нарезка кадров                           |
| 1–2  | Нейросети: глаза системы                             |
| 3–5  | Обычный код: превращаем боксы в лог действий         |
| 6–7  | Поиск нарушений: правила + LLM                       |
| 8    | VLM: проверка глазами                                |
| 9–10 | Обычный код: оформление ответа                       |
